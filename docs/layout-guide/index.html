linux-lit — Reader Layout Guide

An orientation for a UI/UX designer new to the project. How the GTK4 reader card is structured, how the two-column “book-spine” mode works, how lines are styled, and which numbers you can safely change.

What linux-lit is: a GTK4 + Rust e-reader for Shakespeare/literature with MPV audio sync and vim-style navigation. The text is rendered inside a centered “card” on a dark wallpaper; verse can render in one wide column (monocle) or two columns (an open-book spread). But the card is not the whole reading surface — floating UI (vocabulary definitions, toasts/notifications, pickers) is placed in the dark space around the card. This guide focuses on the visual layout you’d be designing for.

1. The big picture — a card, plus floating UI in the margins

The reading text lives inside one rounded card, horizontally centered in the window over a dark wallpaper. The card width is derived from the window width; the leftover becomes the dark margins on either side. Those margins are not empty — several pieces of UI are deliberately placed in them: vocabulary definitions sit just right of the card, and toasts/notifications appear in the bottom-left and bottom-right corners of the window.

2. Widget hierarchy (what nests in what)

If you’re reasoning about spacing or adding UI, this is the box tree. The card subtree (content_hbox downward) holds the text; the floating UI is added to a window-spanning overlay via add_overlay, so it can be positioned anywhere — including the dark margins beside and below the card (see §1).

3. How a line is styled

The reader classifies every source line and tags it. As a designer, these are your type styles. They’re applied as GTK TextTags in apply_dialogue_formatting.

4. Two-column “book-spine” mode

On wide windows, verse renders as a two-column spread. The two columns plus a thin divider form a block that is centered in the card. Each column is a fixed width (the verse-safe minimum), so the block sizes to its content and the slack becomes equal outer margins.

Equal vs unequal — the subtle part.
  • card-edge → signs (left) ≈ divider → signs (right): equal. Both are just the sign-gutter offset; the block fills the card so the outer margin ≈ 0.
  • card-edge → signs (left) vs text-end → card-edge (right): unequal. The right side carries the ~80px verse leftover, so its visible margin looks wider.

5. How the column split is decided

Important for a designer to know: the boundary between the two columns is computed by pixel height, not by line count or content. column_split() fills the left column to the available height, then continues the same document into the right column.

  • Left column fills maximally, trimming only a trailing speaker/blank that would orphan.
  • Right column is the bottom of the spread — it may fit one extra line (relaxed guard) to avoid a mid-spread gap.
  • So the two columns are usually equal height; occasionally the right is one line taller. That’s intentional.
  • Page turns advance by whole spreads; a partial bottom line is hidden by a clip bar.

The one hard constraint: verse lines must not wrap. The widest Folger verse line across all 38 plays sets MIN_TWO_COLUMN_COLUMN_WIDTH. Lower it and the longest lines (e.g. in Troilus) will wrap mid-verse, which looks broken. Any width change must be checked against the longest-line works (there are headless pagination tests for this). Prose wraps freely and is not a constraint.

7. Why the single column is a fixed width (not a fraction of the window)

A natural question: the two-column card scales with the window (a fraction), so should the single-column card scale too? No — and the asymmetry is deliberate. The two modes are bound by opposite constraints:

  • Single column → bound by line-length readability. A single column of text has an optimal measure (~50–75 characters per line). Past that, the eye struggles to find the start of the next line. A fixed column_width caps the measure at the readable optimum no matter how wide the monitor is. If it scaled with the window, a 2560px ultrawide would give ~2000px lines of verse — unreadable. (This is how print and Foliate/iBooks/Kindle behave: a page doesn’t widen with your desk.)
  • Two columns → each column is already at its readable width. The constraint is inverted: the columns are fixed at the verse-safe 700px, so the only question is how much of the window the spread occupies. A fraction lets the spread breathe on wide screens without stretching the lines.

So the fixed single-column width is a readability feature, not a missing fraction. Don’t turn it into a window fraction — it would make wide-monitor reading worse.

The real edge case — font size, not window width. column_width is a fixed pixel value, but the readable measure is a character count, and characters scale with font size. So the measure drifts as the user changes the font:
  • Default font is 16pt Charter in a 1050px card → roughly ~80 chars/line (already a touch above the ideal 50–75 band).
  • At a large font (e.g. 24pt) the same 1050px holds ~55 chars/line — back in the sweet spot.
This means the single column is sized well for large fonts but slightly wide at the default. If you ever want “perfect” measure, the lever is to make column_width respond to font_size (target a character count, e.g. ~66ch), not to window width. It’s a minor, separate concern — flagged here so a designer doesn’t reach for the wrong knob.

8. Theme & color

Colors come from a unified theme JSON (light/dark variants), applied as CSS at runtime. The reader card is a warm paper tone; text is a muted ink; an accent (“root”) color marks vocab and highlighted words; the cursor line is a soft tint. When you propose color changes, they belong in the theme system, not hardcoded.
